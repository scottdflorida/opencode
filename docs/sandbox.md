# Phase 4 execution boundary

Status: worker integration pending. The current ProjectCopy worktree isolates Git state, while direct V2 tools and, by default, configured checks execute with the host user's authority. A repository must be trusted before unattended execution in the current implementation. Setting `orchestration.execution_trust` to `untrusted` rejects assignment submission, run starts, and attempt or preset check execution until an isolated worker is available; the omitted setting retains the existing trusted-host behavior.

## Worker contract

Use a disposable VM-backed worker for attempts and checks on repositories that are not trusted. The controller owns the durable run and chooses routes; the worker receives one attempt's base commit, task instructions, bounded tool permissions, and selected check names. It returns a patch or commit, bounded logs, check results, process exit status, and resource usage. The controller verifies the returned Git base and patch before it records the attempt. User-selected integration stays on the host after preflight.

The worker can write only its attempt workspace and a disposable scratch directory. The source checkout, host home directory, SSH agent, provider credentials, `.env`, and orchestration database are never mounted. A host-side broker owns model and judge credentials. Untrusted commands have no direct network access; a separately reviewed broker path is required for model or harness traffic. This means a harness that cannot use the broker is ineligible for untrusted runs rather than silently falling back to host execution.

The controller must use this boundary for all code execution in an untrusted run: direct V2 tool commands, harness subprocesses, baseline and attempt checks, and any conflict-resolution attempt. A worktree or an environment-variable allowlist alone cannot satisfy it. Route observations must record which boundary executed an attempt and reject a route when its required worker is unavailable.

## Rollout

1. Add an explicit project trust setting and a worker capability observation. The config setting now fails closed for untrusted work; worker capability observation remains. Existing configurations retain trusted-host behavior.
2. Materialize a repository snapshot inside a disposable worker. The opt-in `orchestration.check_runtime: "colima"` now transfers a bounded snapshot through Docker stdin and runs deterministic checks in an unprivileged container with no direct network, host mount, or Docker socket. It uses the pinned official Bun 1.3.14 Alpine image and never pulls an image during a check. Shell and self-contained Bun checks work; checks needing repository dependencies require a purpose-built image. Snapshot transfer for untrusted, model-edited work remains to be hardened before the untrusted switch can be enabled.
3. Move direct V2 tool execution into the worker. Enable each harness only after its authentication and network path works without mounting host credentials.
4. Check filesystem, network, process, timeout, cleanup, and patch-import boundaries with disposable repositories before allowing unattended untrusted runs.

Colima, Lima, and the Docker CLI are installed on this Mac. The dedicated `jewelcode` Colima profile runs with macOS Virtualization.Framework, two CPUs, 4 GiB of memory, a 20 GiB disk, no host mounts, no forwarded SSH agent, no port forwarding, and no activated default Docker context. Its socket is `~/.colima/jewelcode/docker.sock`; use `docker --context colima-jewelcode` to target it. A disposable Alpine container with `--network none`, a read-only root filesystem, dropped capabilities, no new privileges, and process and memory limits had no host home or Docker socket in its filesystem and no IP route. The opt-in check runner passed a disposable repository preset and excluded both root and nested `.env` files. This verifies a narrow check path, not the full worker boundary. `sandbox-exec` exists but [Apple marks it deprecated](https://developer.apple.com/forums/thread/661939). The host-side credential broker, safe snapshot and artifact transfer for model-edited attempts, and direct V2 tool and harness execution paths still need implementation before the `untrusted` setting can run work.
